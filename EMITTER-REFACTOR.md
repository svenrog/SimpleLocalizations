# Planned: cut what the emitter allocates

Work not yet started. Delete this file in the commit that finishes it.

## Why

`VocabularyEmitter` allocates about **4 KB per key**, which is most of what generating a vocabulary costs.
Measured with `bench/SimpleLocalizations.Benchmarks`:

| Keys | Cold generation | Allocated |
| --- | --- | --- |
| 1 000 | 2.9 ms | 3.9 MB |
| 100 000 | 636 ms | 388 MB |

At a realistic size this buys about 3 ms, which is not on its own worth a rewrite. It is worth doing because
the cost is **avoidable rather than inherent** — the emitter builds a string per line to append it to a
buffer — and because a build that grows its vocabulary should not find a cliff.

The second run is already flat at ~2.6 µs whatever the resource holds, so **none of this touches the number
that decides whether an IDE stutters**. This is the cold path a build pays once.

## Where the allocations are

Every one of these is per emitted line, and there are roughly ten lines per key:

1. **`AppendLine($"…")`** — the interpolation builds a whole string, which `AppendLine` then copies into the
   buffer and discards. This is the bulk of the 4 KB.
2. **`new string(' ', indent * 4)`** in `Write` — one padding string per node, recomputed at every level.
3. **`Escape`** — three `Replace` calls per documented member, each allocating whether or not the text holds
   the character it is replacing. Most comments hold none of them.
4. **Buffer growth** — the `StringBuilder` starts empty and doubles, so a 20 MB result is reached by copying
   about 40 MB. The final `ToString()` and `SourceText.From` then copy it twice more.

## Phase one: widen the test surface

Part of the work rather than a gate on it, and the half that decides whether the rest is low risk.

The existing tests assert **fragments** of the emitted source (`Assert.Contains("public static class Alpha")`
and about twenty more). That is the right shape for the features — it is why the emitter can be rewritten at
all without rewriting the suite — but it does not pin the whole document, so a rewrite can change the output
in ways nothing notices. Three gaps, each a commit of its own:

1. **A golden test.** Assert the complete emitted text for one vocabulary exercising every branch: a flat
   key, a two-level family, a three-level family, a documented entry, an undocumented one, a reserved-name
   segment, a digit-leading segment, a per-family key type, and a resource name. After that the rewrite is
   verified by the diff being empty, which is what makes it low risk rather than merely well tested.

2. **The generated-file headers.** Nothing currently asserts that the output opens with `// <auto-generated/>`
   and `#nullable enable`. The first is load-bearing and not obviously so: `VocabularyKeyGuard` calls
   `ConfigureGeneratedCodeAnalysis(GeneratedCodeAnalysisFlags.None)`, and Roslyn decides what is generated
   partly from that marker. Drop the line and **`SL1010` starts firing on the generated declaration itself**,
   which is the one caller allowed to produce a key. Pin both lines.

3. **A deep vocabulary that compiles.** `DocumentedExamplesTests` compiles generated source, but only the
   two-key fixtures the documentation shows. Add one that compiles a vocabulary four levels deep with a
   hundred keys, so indentation and nesting are checked by the compiler rather than by a substring.

## Phase two: the change itself

Ordered so each step is separately measurable, and none of them changes a character of output:

1. **Append parts instead of interpolating.** `AppendLine($"{pad}public static class {name}")` becomes
   `builder.Append(pad).Append("public static class ").AppendLine(name)`. Mechanical, and the largest win.
2. **Cache the padding.** Depth rarely exceeds four; hold an array of pad strings and grow it on demand.
3. **Escape only when there is something to escape.** Scan for `&`, `<` and `>` first and return the input
   when there is none, which is the common case.
4. **Pre-size the builder.** `new StringBuilder(entries * 250)` or thereabouts, measured rather than guessed,
   so the buffer is not reached by repeated doubling.

## How to know it worked

- The golden test passes **unchanged**. If it does not, the rewrite changed the output and the diff is the
  thing to review — not the test to update.
- `dotnet run -c Release -- --filter *GeneratorBenchmarks*` before and after. Expect the per-key allocation
  to fall well below 4 KB; cold time follows it down, since most of that time is GC.
- The 100 000-key case is the one that shows the shape. It is not a size anyone will author.

## Not in scope

- **`SourceText.From`.** It copies the finished string, and avoiding it means giving Roslyn a stream. That is
  a separate question with its own risk, and it is not where the allocations are.
- **The incremental path.** Already flat at ~2.6 µs and 3.46 KB from ten keys to a hundred thousand. Nothing
  here should change it, and the caching tests will say so if it does.
- **Anything about what is emitted.** This is a rewrite of how the text is built. A change to what the text
  says belongs in its own commit, before or after, never inside this one.
